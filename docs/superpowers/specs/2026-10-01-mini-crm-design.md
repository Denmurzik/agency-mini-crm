# Мини-CRM для заявок агентства — дизайн

Дата: 2026-10-01 · Статус: на ревью

## 1. Цель и критерии успеха

Тестовое задание «вайбкодер»: за 3 дня от идеи до работающего MVP по живой ссылке.

Проверяющий оценивает: понятен ли контур продукта, работает ли MVP по ссылке, виден ли собственный ход мысли.

MVP считается готовым, когда проверяющий может сам, без нашей помощи:

1. Написать боту → пройти диалог → увидеть лида в CRM (без ручного обновления страницы) с тегом услуги.
2. Завести лида руками, повесить/снять тег, отфильтровать список по тегу.
3. Написать в личку подключённого Telegram-аккаунта → увидеть лида в CRM.

Сдача: Google Doc (набросок продукта + разбор) + ссылка на CRM + ссылка на бота + ссылка на публичный репозиторий.

## 2. Архитектура

```
 Клиент ─► @бот ──webhook──►┐
                            │   Vercel: Next.js ─────────────► Neon Postgres
 Клиент ─► личный Telegram  │   ├ /api/telegram/webhook   бот (шаг диалога в БД)
           менеджера        │   ├ /api/ingest   ◄── единая точка создания лида
              ▲ MTProto     │   └ CRM UI за паролем
 Railway: worker (GramJS) ──┘          │
              ▲  HTTP (Bearer) ────────┘  подключение аккаунта из UI
```

Принципы:

- **Одна точка входа лида — `ingestLead()`.** Бот вызывает её напрямую, воркер — через `POST /api/ingest`, ручное добавление — через server action. Дедуп, автотеги, уведомления живут только там. Новый канал = новый тонкий адаптер.
- **Дедуп по Telegram user id.** Один человек = одна карточка, независимо от того, писал он боту или в личку. Повторные обращения добавляются в историю.
- **Изоляция отказов.** Воркер — отдельный сервис. Если он упал, отваливается только пункт 2; бот, CRM и ручной ввод работают.
- **Serverless-совместимость.** На Vercel нет памяти между запросами: состояние диалога бота хранится в БД, webhook идемпотентен.

## 3. Модель данных (Postgres, Drizzle)

| Таблица | Поля | Заметки |
|---|---|---|
| `leads` | `id`, `name`, `contact`, `request`, `source` (`bot`/`telegram`/`manual`), `status` (`new`/`in_progress`/`won`/`lost`), `tg_user_id` (bigint, unique, null), `tg_username`, `is_demo`, `created_at`, `updated_at`, `last_activity_at` | `tg_user_id` — ключ дедупа |
| `tags` | `id`, `name` (unique, без учёта регистра), `color` | |
| `lead_tags` | `lead_id`, `tag_id` (PK пара) | каскадное удаление |
| `messages` | `id`, `lead_id`, `source`, `text`, `external_id`, `created_at` | история обращений; unique(`source`, `external_id`) — идемпотентность |
| `bot_sessions` | `chat_id` (PK), `step`, `data` (jsonb), `updated_at` | состояние диалога бота |
| `notify_subscribers` | `chat_id` (PK), `created_at` | кому слать уведомления о лидах |
| `tg_accounts` | `id`, `phone`, `tg_user_id`, `username`, `display_name`, `session_enc`, `status` (`connected`/`disconnected`/`error`), `last_seen_at`, `created_at` | сессия зашифрована AES-256-GCM, ключ только у воркера |

## 4. Компоненты

### 4.1 `ingestLead()` — ядро

Вход: `{ source, name, contact?, request?, tgUserId?, tgUsername?, tags?: string[], message?: { text, externalId } }`.

Логика:

1. Если есть `tgUserId` и лид с ним уже существует → обновить пустые поля (имя/контакт), добавить сообщение в историю, добавить теги, обновить `last_activity_at`. Если лид был закрыт (`won`/`lost`) — вернуть в `new`. Результат: `{ lead, created: false }`.
2. Иначе создать лида со статусом `new`, теги (создаются при отсутствии), первое сообщение. Результат: `{ lead, created: true }`.
3. Повтор `message.externalId` — no-op (защита от ретраев).
4. Отправить уведомление подписчикам: «Новый лид» или «Повторное обращение» (ошибка отправки не роняет создание лида).

### 4.2 Бот (grammY, webhook)

Диалог — чистая функция-автомат `step(state, input) → { state, reply }` (тестируется без Telegram), grammY только доставляет апдейты и отправляет ответы.

Шаги:

1. `/start` → приветствие + выбор услуги кнопками: Сайт / Реклама / SMM / Другое. **Услуга = тег лида.**
2. Имя → кнопка «Использовать имя из Telegram» или текст.
3. Контакт → кнопка «Поделиться номером» (request_contact), кнопка «Писать сюда в Telegram» (берём @username), или текст.
4. Запрос → свободный текст.
5. Итог → карточка заявки + кнопки «Отправить» / «Заполнить заново» + строка о согласии на обработку персональных данных.
6. «Отправить» → `ingestLead()` → «Заявка №N принята, менеджер свяжется».

Края: `/cancel` сбрасывает диалог; не-текст (стикер, фото) на текстовом шаге → подсказка; повторный `/start` в середине диалога начинает заново; webhook проверяет `X-Telegram-Bot-Api-Secret-Token`; на ошибке логируем и отвечаем 200, чтобы Telegram не устраивал шторм ретраев.

`/start notify_<token>` — подписка на уведомления (см. 4.5).

### 4.3 Воркер (Railway, Node + GramJS)

- При старте загружает аккаунты из `tg_accounts`, расшифровывает сессии, подключается, вешает обработчик новых сообщений.
- Фильтр `shouldIngest(message)` (чистая функция, тестируется): входящее (`!out`), личный чат, отправитель не бот, не сам аккаунт, не служебный (777000), **не в контактах** (друзья — не лиды).
- Лид: имя из профиля, контакт = `@username` или телефон (если виден), запрос = текст первого сообщения; не-текст → «[фото]», «[голосовое]» и т.п. Отправка в `POST /api/ingest` с `Bearer INGEST_SECRET`.
- Heartbeat: раз в 30 с обновляет `last_seen_at`.
- HTTP API (Bearer `WORKER_SECRET`, вызывается только с сервера CRM):
  - `POST /auth/send-code { phone }` → клиент держится в памяти до завершения входа;
  - `POST /auth/sign-in { code }` → `{ ok } | { needPassword: true }`;
  - `POST /auth/password { password }` → 2FA;
  - `POST /auth/logout` → выход и удаление сессии;
  - `GET /status`.

### 4.4 CRM (Next.js App Router, Tailwind + shadcn/ui)

- **Вход** по одному паролю (`CRM_PASSWORD`) → httpOnly-cookie с HMAC-подписью; middleware закрывает всё, кроме `/login`, `/api/telegram/webhook`, `/api/ingest`, `/api/health`.
- **Лиды** — таблица: имя, контакт, источник, статус, теги, дата. Фильтры: чипы тегов со счётчиками, статус, источник, поиск по имени/контакту/запросу; фильтры живут в URL (`?tag=сайт`) — ссылкой можно поделиться. Автообновление опросом каждые ~4 с; новый лид подсвечивается и всплывает тост.
- **Карточка лида** (боковая панель): правка полей, смена статуса, теги (добавить существующий / создать новый / снять), история сообщений, «Открыть в Telegram».
- **«+ Лид»** — форма ручного добавления (имя обязательно, контакт, запрос, теги).
- **Каналы**: бот (ссылка, статус webhook), подключённый Telegram-аккаунт (статус по heartbeat, «Подключить» → телефон → код → пароль 2FA, «Отключить»), уведомления («Подписаться» → deep link в бота).
- **Демо-данные**: ~10 лидов с тегами, статусами и пометкой «демо»; сид-скрипт.

### 4.5 Уведомления менеджеру

На странице «Каналы» кнопка «Получать уведомления в Telegram» открывает `t.me/<bot>?start=notify_<token>`, где `token` — HMAC от секрета. Бот проверяет токен и сохраняет `chat_id` в `notify_subscribers`. Случайный пользователь бота подписаться не может. Уведомление: имя, контакт, запрос, теги, ссылка на карточку.

## 5. Безопасность и персональные данные

- CRM за паролем, пароль выдаётся в документе.
- Сессия Telegram-аккаунта шифруется, ключ только в env воркера.
- Все межсервисные вызовы — с секретами (webhook secret token, `INGEST_SECRET`, `WORKER_SECRET`).
- Бот показывает строку о согласии на обработку данных перед отправкой.
- Для пункта 2 рекомендуется подключать рабочий/второй аккаунт: userbot — неофициальный клиент, с серверного IP есть риск ограничений.

## 6. Тестирование

- Vitest на логику без внешних зависимостей: автомат диалога бота, `shouldIngest`, токен подписки.
- `ingestLead()` (дедуп, теги, идемпотентность, переоткрытие) — интеграционные тесты на PGlite (Postgres в процессе, без Docker).
- Сквозная проверка вручную на проде: сообщение боту → лид с тегом в CRM; ручной лид; фильтр по тегу; сообщение в личку → лид. Результаты фиксируются скриншотами для документа.

## 7. Стек и деплой

- Next.js (актуальная версия) + TypeScript + Tailwind + shadcn/ui, Drizzle ORM, Neon Postgres (через Vercel Marketplace), grammY.
- Воркер: Node 22 + `telegram` (GramJS) + `postgres`, деплой на Railway из папки `worker/`.
- Публичный GitHub-репозиторий с README (архитектура, запуск, env).
- Скрипты: `set-webhook` (с `secret_token` и `allowed_updates: message, callback_query`), `seed`.

## 8. Сознательно за скобками

Ответ лиду из CRM (двусторонний чат), несколько пользователей и роли, несколько воронок и канбан, аналитика, вложения (храним только текст и пометку типа), несколько подключённых аккаунтов в UI (модель данных позволяет), WhatsApp / формы с сайта (точка расширения — `ingestLead()`), Telegram Business как альтернатива userbot (требует Premium).

## 9. План

- **День 1:** каркас, БД, `ingestLead()`, бот, CRM (лиды, теги, ручное добавление, статусы, фильтры), деплой на Vercel — обязательные пункты 1, 3, 4 работают по ссылке.
- **День 2:** воркер + подключение аккаунта из UI, уведомления, демо-данные, полировка.
- **День 3:** документ (набросок + разбор) со схемой и скриншотами, финальный прогон, запас.

## 10. Изменение по ходу: пункт 2 через Telegram Business

my.telegram.org не выдал `api_id` (постоянный ERROR), поэтому основным способом для пункта 2 стал **Telegram Business**. Владелец (с Premium) привязывает бота в «Настройки → Telegram для бизнеса → Чат-боты», и Telegram присылает на тот же webhook `business_connection` и `business_message`.

- Подключения хранятся в `tg_business_connections`; неизвестное подключение подтягивается через `getBusinessConnection`.
- Входящее от собеседника → `ingestLead({ source: "telegram", externalId: "biz:<conn>:<chat>:<msg>" })`; исходящие владельца, боты и группы игнорируются.
- Бот **никогда не отвечает** в бизнес-чатах (ответ ушёл бы от имени владельца).
- Фильтр «не из контактов» задаёт владелец в настройках Telegram («все кроме контактов») — Bot API не сообщает, контакт ли отправитель.
- Userbot-воркер (`worker/`) остаётся запасным путём для аккаунтов без Premium.
